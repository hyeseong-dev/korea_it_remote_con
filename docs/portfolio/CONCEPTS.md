# 개념과 표현 해설

[통합 포트폴리오 글](CASE_STUDY.md)을 읽을 때 혼동하기 쉬운 용어와 주장 범위를 정리한 문서다. 구현 기준은 v2.0.0이며, 아래의 '지원'은 별도 언급이 없으면 코드에 구현되어 있다는 의미다. 실제 운영체제에서 접속까지 검증했다는 의미와는 구분한다.

## 1. 이 애플리케이션은 무엇을 만드는가

이 프로젝트는 원격 화면 전송 프로그램이 아니라 **원격 접속 앱을 실행하기 위한 연결 준비 도구**다. 사용자가 장치 별칭을 고르면, 로컬 설정에서 주소와 경로를 읽고 필요한 점검을 수행한 뒤 AnyDesk를 연다.

- 우리가 구현한 부분: 설정 검증, 경로 선택, 제한 시간 내 TCP 검사, OS별 앱 탐색·실행, 결과 구분.
- Tailscale의 역할: 장치 사이에 통신할 네트워크 경로 제공.
- AnyDesk의 역할: 원격 접속 인증, 화면 전송, 키보드·마우스 입력 전달.
- 원격 OS의 역할: 사용자 세션과 프로그램 실행, 시스템 권한 관리.

따라서 '애플리케이션으로 문제를 해결했다'는 기존 도구를 연결하고 반복 작업을 일반화했다는 뜻이다. 자체 VPN이나 화면 전송·암호화 프로토콜을 개발했다는 뜻이 아니다.

## 2. 연결을 이해하는 네 가지 질문

| 단계 | 질문 | 이번 프로젝트의 예 | 성공해도 보장되지 않는 것 |
| --- | --- | --- | --- |
| 네트워크 도달 | 대상 주소와 포트에 통신할 수 있는가? | TCP 7070 검사 | AnyDesk 인증과 화면 세션 |
| 앱 실행 | 접속 앱에 실행 요청을 전달했는가? | macOS open 또는 실행 파일 호출 | 원격 서버 접속 성공 |
| 인증 | 접속 요청자의 신원을 확인할 수 있는가? | AnyDesk 암호 또는 기존 앱 인증 | 모든 작업 권한 |
| 인가와 세션 | 어떤 작업을 허용하고 실제 화면 세션을 열었는가? | 화면 보기·입력 권한으로 원격 조작 | 재부팅·장애 후에도 항상 접속 가능 |

'연결됐다'라고만 쓰면 이 단계가 섞인다. 글에서는 'TCP 도달 확인', '앱 실행 요청 성공', 'AnyDesk 화면 세션 확인'처럼 관측 대상을 붙인다.

### CLI 상태값 읽기

| 상태 | 정확한 의미 |
| --- | --- |
| `dry_run` | 설정 검증과 앱 탐색 완료. 네트워크 검사·파일 생성·앱 실행은 하지 않음 |
| `reachable` | 선택한 주소의 TCP 포트에 연결할 수 있었음 |
| `unreachable` | TCP 검사 실패 또는 시간 초과. 원격 PC가 꺼졌다는 단정은 불가능 |
| `not_probed` | 중계 경로라 TCP 사전 확인을 생략함. 중계 서비스 정상 여부는 확인하지 않음 |
| `launched` | AnyDesk 실행 요청을 전달함. 인증 또는 화면 연결 완료는 아님 |
| `client_missing` | 사용할 로컬 AnyDesk 앱을 찾지 못함 |
| `invalid_config` | 지원하지 않는 필드·주소 형식 등 설정 검증 오류 |
| `unsupported_platform` | 지원하는 세 OS 이외의 환경 |
| `unknown_device` | 요청한 장치 별칭이 프로필에 없음 |
| `unknown_route` | 해당 장치에 요청한 경로 이름이 없음 |
| `launch_failed` | 클라이언트 실행 요청 또는 바로가기 준비가 실패함 |

v2 CLI는 `connected`나 `authentication_required` 상태를 자동 검출하지 않는다. 앞선 설계에서 고려한 상태와 실제 구현 상태를 구분해야 한다. macOS 실행 요청의 완료와 Windows/Linux 자식 프로세스 생성 역시 앱 내부 성공을 증명하지 않는다.

## 3. 네트워크 용어

### 주소, 포트, 프로토콜

주소는 통신할 대상을 찾는 정보다. 포트는 그 장치에서 통신할 서비스의 번호다. 프로토콜은 양쪽이 메시지를 주고받는 규칙이다. '포트가 열렸다'는 TCP 연결 검사에 응답했다는 뜻으로 사용하며, 그 서비스의 인증에 성공했다는 뜻이 아니다.

현재 도구는 직접 경로에 TCP 7070을 사용한다. 검사 포트와 실제 AnyDesk 실행의 목적지가 어긋나는 문제를 피하기 위해 사용자 지정 포트는 지원하지 않는다.

### Tailscale과 SSH, RDP, AnyDesk

Tailscale은 네트워크 경로를 제공한다. SSH는 관리 명령을 실행하는 데 사용한 접속 방식이고, RDP와 AnyDesk는 GUI 접속 후보였다. 같은 범주의 대체재로 나열하면 혼동된다. 예를 들어 Tailscale 위에서 SSH나 AnyDesk 통신을 할 수 있다.

기존 SSH 키로 관리자 인증에 성공한 것은 해당 SSH 서비스가 그 키를 받아들였다는 뜻이다. 그 키가 RDP 암호를 대신하거나 다른 앱의 인증을 자동 통과하게 하는 것은 아니다.

### 직접 연결과 중계 연결

직접 연결은 이 글에서 해당 네트워크 계층의 중계 서버 없이 장치 간 통신하는 경로를 뜻한다. 중계 연결은 중간 서버가 트래픽을 전달하는 경로다. '직접'이라는 표현에는 어느 계층인지 붙여야 한다.

- Tailscale 직접 연결: Tailscale이 장치 간 직접 경로를 사용한 관측.
- Tailscale DERP 중계: Tailscale 트래픽이 중계 서버를 거친 관측.
- AnyDesk 직접 주소 연결: AnyDesk에 Tailscale 주소를 지정한 것. 아래 Tailscale 경로까지 직접 연결이라고 보장하지 않음.
- AnyDesk ID 중계: 비상 경로에서 ID와 `/np`를 사용해 AnyDesk 중계를 요청한 것.

DERP는 이 사례에서 관측한 Tailscale 중계 경로의 이름이다. NAT는 내부 주소와 외부 주소를 변환하는 네트워크 동작이며, 방화벽은 규칙에 따라 통신을 허용·차단하는 기능이다. 둘은 다르다. 중계 사용만으로 학원 보안 프로그램이 차단했다고 단정할 수 없다.

### 주 경로와 비상 경로

주 경로는 기본으로 선택한 경로이고, 비상 경로는 필요할 때 사용자가 별도로 선택하는 경로다. 자동 장애 감지·자동 전환은 구현하지 않았다.

'비상 경로가 독립적이다'는 현재 구현에서 Tailscale TCP 검사를 요구하지 않는다는 의미다. 원격 PC 전원, 인터넷, OS, AnyDesk 앱 장애는 여전히 공통 원인일 수 있다. Tailscale을 실제로 끈 상태의 복구 시험까지 완료했다는 의미는 아니다.

또한 `transport: tailscale`은 설정상의 분류다. CLI가 Tailscale 설치·로그인·실제 패킷 경유를 확인하거나 강제하지는 않는다.

## 4. 보안과 인증 용어

### 인증과 인가

인증은 '누가 접속하는가'를 확인하는 과정이다. 인가는 '접속한 사람이 무엇을 할 수 있는가'를 결정한다. AnyDesk 무인 접속 암호와 화면 입력 권한을 구분하면 이해하기 쉽다.

무인 접속은 인증을 없앤 접속이 아니라, 현장 사람이 매번 승인하지 않아도 사전에 설정한 인증으로 접속하는 방식이다. 이번 최초 설정은 기존 SSH 관리 인증과 사용자의 명시적 승인 후 수행했다. 승인 절차를 무력화하는 코드를 만든 것이 아니다.

### 최소 권한과 보안 경계

최소 권한은 필요한 작업만 할 수 있게 허용 범위를 줄이는 원칙이다. AnyDesk 프로필의 입력 권한을 제한했다고 원격 Windows 계정까지 최소 권한이 되는 것은 아니다. 당시 원격 세션은 관리자 계정이었다.

보안 경계는 데이터나 권한의 취급 규칙이 달라지는 구분이다. 이번 도식에서는 공개 Git 저장소, 로컬 설정, 앱 인증, 원격 권한 검사를 나눈다. 그림에 경계선을 그렸다는 사실이 실제 접근 통제를 보장하지는 않는다. 각각을 어떤 코드·권한·운영 절차로 제한했는지 함께 설명해야 한다.

### .gitignore와 파일 권한

`.gitignore`는 지정한 미추적 파일을 일반적인 Git 추가 대상에서 제외하는 규칙이다. 암호화가 아니며 이미 커밋된 정보나 강제 추가를 막지 않는다.

macOS에서 생성하는 파일의 `0600`은 소유자 읽기·쓰기, 디렉터리 `0700`은 소유자 읽기·쓰기·진입 권한을 뜻한다. 암호화나 다른 OS의 동일한 접근 통제까지 보장하지 않는다. 기존 평문 암호 파일은 로컬에 남아 있고 새 CLI가 읽지 않는다.

### 인수 배열과 입력 검증

셸 문자열로 명령을 조합하면 특수 문자가 명령으로 해석될 수 있다. 현재 코드는 실행 파일과 인수를 배열로 전달하고 주소 형식을 제한한다. 그러나 이것만으로 실행 파일이 신뢰할 수 있는 프로그램인지 보장하지는 않는다. 사용자 지정 앱 경로의 신뢰는 별도 전제다.

## 5. 소프트웨어 설계 용어

| 용어 | 이 프로젝트에서의 의미 | 오해하면 안 되는 점 |
| --- | --- | --- |
| 계층(layer) | 책임에 따라 나눈 코드 구성 | 모든 계층이 네트워크 서버나 패킷 중계는 아님 |
| 추상화 | 장치 별칭으로 선택하고 OS 내부 실행 차이를 감춤 | OS 차이를 실제로 없앤 것은 아님 |
| 어댑터 | 공통 요청을 OS가 실행할 수 있는 방식으로 변환 | 현재는 `platforms.py`의 분기이며 독립 플러그인 시스템은 아님 |
| 프로필 | 대상·경로·인증 방식·앱 위치에 관한 로컬 설정 | 로그인 세션이나 OS 사용자 프로필과 다른 뜻 |
| 제공자(provider) | 화면 제어를 담당하는 앱 종류 | 현재 AnyDesk 하나만 구현 |
| 하드코딩 | 환경에 따라 달라질 값을 코드에 고정 | 기본값이나 검증된 프로토콜 상수까지 모두 제거할 필요는 없음 |
| 이식성 | 공통 사용법과 구조를 다른 환경에 적용할 수 있는 정도 | 모든 환경에서 같은 성공률·기능을 보장하지 않음 |
| 의존성 | 실행에 필요한 프로그램·환경 | Python 표준 라이브러리만 써도 Python과 AnyDesk는 필요 |

'OS 독립적'보다는 '공통 CLI와 OS별 실행 어댑터를 분리했다'가 정확하다. 소스 인터페이스는 공통이지만 Windows/Linux는 모의 테스트만 수행했다. 또한 커밋된 v1도 실제 IP를 바로가기 파일에서 읽는다. v2의 차이는 주소 제거 자체보다 여러 장치와 경로를 공통 구조로 다루는 데 있다.

## 6. 검증과 성과를 표현하는 방법

| 모호하거나 과장될 수 있는 문장 | 권장 표현 |
| --- | --- |
| 모든 OS에서 작동한다 | 세 OS용 실행 어댑터를 구현했고 Mac 실환경과 Windows/Linux 명령 생성 모의 테스트를 확인했다 |
| Tailscale 연결을 확인했다 | 해당 프로필 주소의 TCP 포트 도달을 확인했다. 실제 경유 확인은 별도다 |
| 자동으로 접속한다 | 앱 실행까지 자동화했다. 인증과 화면 세션은 AnyDesk가 담당한다 |
| 장애에 강하다 | 명시적으로 선택할 비상 경로를 추가했다. 완전한 장애 복구 시험은 남아 있다 |
| 보안 문제를 해결했다 | Git 공개 범위·입력 검증·파일 권한·인증 책임을 구분했다 |
| 성능이 70% 좋아졌다 | 서로 다른 시점에 중계 약 74~78ms와 직접 약 21ms를 관측했다 |
| 테스트로 검증했다 | 14개 테스트에서 설정·실행 계획·오류 처리를 확인했다. 실제 GUI·성능·전체 보안 검증은 아니다 |

ping은 네트워크 왕복 응답 시간의 관측이다. CPU 사용량, 화면 인코딩, 입력 반응, 재접속 안정성과 같은 GUI 품질 전체를 뜻하지 않는다. 서로 다른 시점의 수치를 앱 변경의 효과로 해석하려면 통제된 비교가 추가로 필요하다.

## 7. 다이어그램 읽기와 이번 Mermaid 오류

시퀀스 다이어그램은 '언제 누구에게 요청하는가', 아키텍처 도식은 '어떤 구성 요소가 어떤 책임을 갖는가', 보안 도식은 '정보와 권한을 어디서 제한하는가'를 설명한다. 논리 흐름을 그린 그림은 패킷 캡처나 런타임 검증의 대체물이 아니다.

이번 오류는 시퀀스 메시지의 세미콜론을 Mermaid가 명령 구분자로 해석하면서 발생했다.

```text
수정 전: C-->>U: unreachable; 종료
수정 후: C-->>U: unreachable, 종료
```

세미콜론을 반드시 표시하려면 공식 문법의 `#59;`를 쓸 수 있다. 이번 문서에서는 불필요한 문법 의존성을 줄이기 위해 쉼표로 바꿨다. 실패 시 종료를 뜻하는 `break ... end` 블록은 유지했다. 같은 표현이 있던 기획서도 함께 수정했다. [Mermaid 공식 시퀀스 문법](https://mermaid.js.org/syntax/sequenceDiagram#entity-codes-to-escape-characters)

2026-09-06 Mermaid 11.17.2 파서에서 수정 전 오류를 재현했고, 수정 후 통합 글과 기획서의 다이어그램 6개가 모두 통과했다. 검증 도구는 임시 폴더에 설치했으며 프로젝트 런타임 의존성에는 추가하지 않았다.

파서 검증은 문법 오류가 없는지 확인하는 것이다. 사용하는 문서 뷰어의 Mermaid 버전, 폰트, 레이아웃까지 동일함을 보장하지 않는다.
